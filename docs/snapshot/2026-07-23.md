## 1. 项目定位

Story Engine 是一个“世界状态权威、多角色自主行动、叙事由状态演化产生”的通用故事模拟引擎。

作者提供人物、欲望、关系、地点、对象、世界规则和少量初始矛盾；角色 Agent 负责理解处境和提出行动，Host/ECS 负责合法性、概率、资产、关系、协议、事件和最终事实，叙述层只渲染已经发生的事情。

长期目标是：一个较小的故事种子能够依靠角色目标、关系、义务和世界事件，自然生长为连贯故事，而不是依赖预写分支树或全能 GM 推剧情。

## 2. 当前核心原则

- 世界真相属于 ECS/Host，不属于 LLM、Hermes 或 GM 文本。
- 行为角色必须同时是 ECS Entity、拥有 `AgentController`，并绑定 live `AgentRegistry` runtime。
- Agent/Hermes 负责理解、动机、计划和候选行动，不能宣布行动成功或直接修改世界。
- GM 只补充真正开放的语义结算；Host 负责规则、概率、随机流、事务和最终提交。
- 时间采用离散事件队列：动作有环境决定的持续时间，同一完成时刻的动作批量结算。
- 被动观察由世界变化按 POV 自动形成；仔细看、搜索、偷听属于主动 `observe`，会消耗行动时间。
- Storylet 是状态空间中的机会/压力提示，不是剧情脚本，也不替角色做决定。
- 关系、义务、协议、情绪、目标、Claim、事件和物品尽量结构化维护，不依赖不可审计的 GM 记忆。
- 核心引擎不认识具体故事；人物、地点、对白和故事专用内容放在独立内容包。

## 3. 权威主循环

默认 Runner 流程大致为：

```text
Input -> ActionScheduling -> Simulation -> Host systems
      -> WorldEvent -> Rendering -> Memory
```

各阶段含义：

1. **Input**：收集玩家输入和 Agent proposal，为每个角色构造 POV-safe perception。
2. **ActionScheduling**：动作进入离散事件队列，环境决定耗时；角色在完成前保持 busy。
3. **Simulation**：结算动作语义；不确定行动由 Host 在合法的成功/失败分支之间抽样。
4. **Host systems**：更新资产、空间、关系、Sentiment、Drive、Obligation、Agreement、Goal、Claim 等权威状态。
5. **WorldEvent**：从已提交的状态变化生成客观 Event Entity，并按 witness/attention 规则投射。
6. **Rendering**：将已提交事实渲染为玩家文本，不允许新增世界变化。
7. **Cognition/Memory**：把角色亲历、看见或合法获知的结果写入私有认知和长期记忆。

Runner 已有整步 checkpoint：权威阶段失败会回滚整步。世界已经提交但 Rendering/Memory 失败时则保留世界历史，生成 `DeliveryReceipt`，通过 `retry_delivery()` 只重试交付阶段，不重复执行角色行动。

公开 step 状态收束为：`aborted`、`rolled_back`、`delivery_failed`、`committed`。

## 4. 角色与 Agent runtime

每个可行动角色必须满足：

```text
ECS Entity <-> AgentController <-> live AgentRegistry runtime
```

旧的 Persona/brain 回退、Narrative/AgentAction 直接行动等旁路已经移除。缺少 live runtime 的自动角色不会偷偷使用另一套决策逻辑，只会留下 `missing_agent_runtime` 诊断。

动态角色必须经过 Host 的 character-entry authorization，以及 `CharacterLifecycle.prepare -> stage -> finalize`。若 ECS 出生、事务提交或 runtime 注册任一阶段失败，整体回滚，避免出现只有“身体”没有“脑”或只有“脑”没有世界实体的半状态。

### Agent 可以做什么

- 根据自己的 perception 和记忆理解处境；
- 生成多个自然语言候选行动；
- 形成或细化私人目标；
- 引用真实动机来源：Goal、Obligation、NavigationProblem、ActionFailure、WorldEvent、EventResponse；
- 选择行动、等待、回避或暂缓。

### Agent 不能做什么

- 宣布成功、失败、概率、骰点或数值 modifier；
- 直接改变位置、物品所有权、关系精确值、宏剧情 或 Goal 状态；
- 读取完整世界、他人秘密或 Host 内部账本；
- 伪造事件、失败经历、义务或其他角色的动机引用。

Host 会校验每个候选的 motive refs。合法引用参与 `CharacterPolicy` 效用计算，非法、过期、异地或属于他人的引用进入审计拒绝列表。

### Hermes/LLM

核心接口是 `CharacterAgentRuntime`。目前有普通 LLM runtime、Hermes runtime 和 Hermes container 适配层，它们共享窄接口，替换 runtime 不应改变 Host 权威边界。

Hermes 的角色是更灵活地理解上下文、生成动机和候选行动，不是世界裁判。目前尚无本快照对应的真实 Hermes 多 seed 长篇证据，因此只能说“接入架构已存在”，不能说“长篇故事质量已证明”。

## 5. 动作、时间和观察

当前原子大动作是：

- `observe`：主动检查、搜索、仔细看、偷听；
- `move`：尝试前往地点；
- `interact`：操作对象、环境或人物；
- `communicate`：说话、报告、解释、请求、道歉、指控等；
- `wait`：等待、观察局势或暂缓。

具体参数可以保留自然语言，但结果由环境规则和 GM/Host 共同结构化结算，最终事实只由 Host 提交。

观察窗口统一为角色在一步中的 `location_before/location_after`。被动观察是 POV 内真实变化的自动投递；主动观察会占用动作，并可能通过观察检定发现隐藏信息。动态出生角色不会看到出生前事件，同场角色也不能读取彼此的隐藏属性。

## 6. Storylet 如何影响剧情

Storylet 代码位于 `src/story_engine/narrative/storylets.py`。当前流程是：

1. 根据 SceneState、Situation 和 one-shot 消费记录筛选可用 Storylet；
2. 按 priority、场景匹配和 beat 提取少量 advisory opportunities；
3. 将这些机会作为上下文/显著性提示，而不是强制任务；
4. 角色仍由自己的目标、关系、义务、事件和人格选择行动；
5. 只有真实行动自然兑现某个机会且世界事务提交成功，Host 才识别 hit；
6. one-shot 仅在成功提交后消费。

因此 Storylet 不会直接推进 宏剧情，也不会替 Agent 决策。GM 自报的 `storylet_hits` 不能成为事实。角色忽略、拒绝或暂缓一个 Storylet 是完整、合法的结果。

Storylet 只由真实世界状态条件激活，并在事务成功后消费；不存在独立的宏剧情时钟。

## 7. 关系、Sentiment、义务和协议

### 关系

关系采用类似《模拟人生》的稀疏双人关系容器：

```text
pair:甲<->乙
  - 甲 -> 乙 directed tracks
  - 乙 -> 甲 directed tracks
  - shared relationship bits
  - interaction timeline
```

`SocialRelationRegistry` 负责惰性创建、查找、事务更新和关系实体维护。常见 tracks 包括 favor、malice、trust。

Agent 和 GM 不会看到精确数值，只看到 Host 派生的 `hostile / wary / non_hostile / trusted / friendly / close` 等定性状态。精确值只用于 Host 策略、概率、衰减和审计。

### Sentiment

感谢、受伤、恐惧、警惕、背叛等即时反应由角色私有 `SentimentState` 维护，不直接等同于永久关系变化。Host 根据有证据的行动和定性强度映射持续时间、衰减及少量长期关系沉淀。

### Obligation

有期限责任由 `ObligationState` 维护，包括 debtor、creditor、deadline、grace、提前唤醒窗口和权威完成条件。它与主观记忆承诺、Timeline 日程分离：

- Timeline：何时可能发生什么；
- Obligation：谁对谁负有什么责任；
- Cognition/Memory：角色自己记得或相信什么。

义务可以完成、取消、违约或通过多方真实行动委托；模型不能单方面宣布履行或替未运行的角色同意。

### Agreement/Contract

旧 `ContractState` 目前只是迁移兼容 adapter，不再是 GM 拥有的 ECS 世界真相组件。正式状态位于独立 Agreement Entity：

- 双人协议可通过 `parent_relation_id` 挂靠双人关系；
- 多方协议挂靠稀疏 Group Relationship；
- 协议自身保存 terms、lifecycle、performance、service、escrow；
- 协议不是塞进关系组件里的一个数组。

普通聊天、试探和含糊承诺留在 Communication/Cognition/Memory。只有明确、跨时、可验证、需要结算的承诺才升级为 Agreement。资产转移、服务义务、托管、退款和违约后果由 Host 原子结算。

## 8. 概率与随机性

概率不能交给 Agent。当前边界是：

- Agent 只表达想尝试什么；
- Host 根据 Trait、能力、风险承受力、Drive、Obligation、关系和环境计算效用或难度；
- 自动角色候选由 `CharacterPolicy` 使用 Session seed 派生的 `policy` 随机流抽样；
- 世界检定和观察检定分别使用独立随机流；
- GM 如需描述不确定行动，必须同时提供成功和失败的合法后果分支；
- Host 抽样并提交其中一支，模型自报 probability、roll、数值 delta 或非法坐标会被过滤。

这样“勇敢如何映射为行动倾向”由可审计函数和随机数控制，而不是依赖 LLM 的伪随机表达。

## 9. 世界状态、物品和事件

有形对象由 `WorldObjectLifecycle` 管理，覆盖创建、搬动、收纳、取出、开合、转交、隐藏、揭示和销毁。每次操作都检查行动证据、地点、容器访问、所有权、可见性、便携性、容量和数量。

空间连通性不能被普通语义更新修改；开路/断路必须经过 `HostTopologyTransaction`。普通世界对象修改经过 `HostWorldEditTransaction`，两者可由 `HostMutationTransaction` 组合为一个原子步骤。

已提交的移动、物品变化、协议生命周期、出席/缺席等会物化为 `WorldEventFact` Entity。事件按真实 witness 投射，不会自动广播给所有角色；知情角色需要通过真实 `communicate` 转述。后续解释、道歉、指控等形成独立 EventResponse，不等于接收者相信、原谅或改变关系。

## 10. 记忆、知识和目标

- `Cognition` 保存角色私有、结构化、POV-safe 的经历和注意事项；
- `Memory` 提供长期检索、显著性排序和低显著旧日志压缩；
- 每个 Session 默认使用独立 memory namespace；
- Claim 是客观命题实体，角色 `KnowledgeState` 只保存 stance、confidence、来源和 evidence；
- 角色只能获得亲历、目击或通过合法沟通传来的知识；
- Goal 由私有 `GoalState` 维护，Agent 可以请求 adopt/refine，但不能提交隐藏完成条件或自行宣布完成；
- Goal 完成/失败由 Host 根据权威状态条件判断；开放目标没有充分证据时会诚实地保持 active。

离屏角色不会每步调用模型。Scheduler 会按 background interval、临近义务、critical Drive、相关 WorldEvent、Goal 续行动或 pending attention 唤醒。重复同类目标行动采用 1×/2×/4×/8×退避，相关且角色确知的事件可重新激活。

## 11. 内容包边界

核心引擎位于 `src/story_engine/`，不应包含具体故事人名、地点、固定对白或角色专属补丁。

故事内容位于独立 `src/story_engine_content/` 包，目前包括：

- `false-heiress`；
- `cthulhu-arkham`；
- `thirteenth-floor`；
- 调查、导航恢复、事件响应、托管服务、目标生长等最小 evaluation seeds。

核心 `src/story_engine/scenarios/` 只保留通用 schema/config。Console/Web 必须显式选择 scenario，不应隐式加载默认故事。

- HEAD 很旧，不能仅靠 Git 历史理解当前设计，应结合工作树代码和本快照。

- README 和设计文档很长，部分段落可能滞后；以实际代码、测试和权威边界为准。
- 真实 Hermes 多 seed 长篇运行尚未充分验证，不能宣称已经证明故事一定有趣、连贯或成本可控。

## 14. 仍然开放的问题

- 真实 Hermes 多角色、长篇、多 seed 的质量、稳定性、延迟和成本。
- motive refs 和 EventResponse 是否在长程运行中真正提高连贯性，而不是增加格式负担。
- 核心层是否仍残留具体故事耦合、旧 API 兼容依赖或手工 宏剧情 推进。
- transcript、episode provenance、sweep/soak 指标是否完全一致。
- 离散时间和主动/被动观察在真实 Agent 调用下的节奏、同步和上下文长度。
- “自然生长为完整故事”仍需要跨 seed 的实证，而不能只靠单次样例或单元测试证明。

## 15. 推荐接手顺序

1. 安装项目依赖，先恢复测试收集能力。
2. 运行 Agent runtime、关系、Agreement、事务回滚、Storylet、WorldEvent 和最小 Episode 定向测试。
3. 阅读 `docs/DESIGN.md`、`docs/AGENT_RUNTIME.md`、`docs/FORMAL_MODEL.md`、`docs/CONTENT_PACKAGES.md`。
4. 从 `src/story_engine/environment/runner.py` 追踪完整 phase chain，再读 Input、Simulation、WorldEvent。
5. 修改行为时优先落在 Host、事务和结构化系统，不要让 Hermes/GM 直接写世界状态。
6. 新故事放到 `src/story_engine_content/`，不要把具体内容塞回核心引擎。
7. 评价故事质量时运行多个 deterministic seed 的 Episode/Sweep，不要只看单次手工对话。

## 16. 最容易误解的三点

1. **Storylet 不是剧情脚本。** 它只是当前状态下的机会/压力提示，角色不响应也合法。
2. **GM 不是最终裁判。** GM 可补充开放语义，最终概率、资产、关系、义务、协议、事件和目标状态属于 Host/ECS。
3. **Contract 不是记忆的替代品。** 含糊承诺留在记忆；只有跨时、明确、可验证、需结算的承诺才升级为 Agreement Entity，并可关联关系实体。
